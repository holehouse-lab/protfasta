# Architecture

This document describes how information moves through **protfasta** during its two everyday operations: reading a FASTA file with `read_fasta` and writing one with `write_fasta`. It is written for someone who wants to change the package rather than use it, so it names the functions involved at each stage and explains why the pipeline is shaped the way it is. The user-facing behaviour of every option is documented on [Read the Docs](https://protfasta.readthedocs.io/); this is about the plumbing behind it.

A few principles run through the whole design and are worth stating up front:

* **Everything that can go wrong raises `ProtfastaException`.** Bad arguments, a missing or unreadable file, a duplicate header, an invalid residue, an output path that cannot be created: one exception type, so callers only ever need one `except` clause. Argument problems are reported before any file is touched; data problems are reported once the file has been parsed.
* **There is exactly one parser.** `read_fasta` and `read_fasta_stream` consume the same line-level engine, so the two can never disagree about what constitutes a record. Likewise there is exactly one record formatter, shared by `write_fasta` and the streaming tee.
* **Records are `[header, sequence]` pairs, and stay that way until the very end.** Every sanitization step takes a list of these pairs and returns a list of these pairs. The dictionary that `read_fasta` returns by default is built in the final step, from whatever survived.
* **Nothing is validated twice and nothing is copied that does not need to be.** Sanitization steps hand the same string objects along; the "remove" steps build new lists of existing entries, the "convert" step rewrites a sequence in place only if something actually changed, and duplicate detection works on 16-byte digests rather than the sequences themselves.

## Layout

| module | role |
|---|---|
| `protfasta/__init__.py` | The public API: `read_fasta`, `read_fasta_stream`, `write_fasta`, plus `ProtfastaException`, `STANDARD_AAS`, `STANDARD_CONVERSION` and `__version__`. `read_fasta` and `write_fasta` are defined here; they orchestrate, they do not parse. |
| `protfasta/io.py` | Everything that touches a file or an argument list: the encoding policy, `check_filename` and `check_inputs`, the line-level parsing engine `_iter_fasta_lines`, the load-everything wrapper `_parse_fasta_all` / `internal_parse_fasta_file`, the record formatter `_format_record`, and the streaming engine `_stream_fasta`. |
| `protfasta/protfasta.py` | The three workflow steps that `read_fasta` runs after parsing: `_deal_with_duplicate_records`, `_deal_with_duplicate_sequences` and `_deal_with_invalid_sequences`. Each one just dispatches on its action string to a utility function and handles the verbose printing. |
| `protfasta/utilities.py` | The functions that do the actual work on a list of records: validation (`check_sequence_is_valid`, `fail_on_invalid_sequences`, `remove_invalid_sequences`), conversion (`_make_converter`, `convert_invalid_sequences`, `convert_to_valid`), duplicate handling (`fail_on_duplicates`, `remove_duplicates`, `fail_on_duplicate_sequences`, `remove_duplicate_sequences`), the digests behind it (`_seq_hash`, `_record_hash`) and `convert_list_to_dictionary`. |
| `protfasta/_configs.py` | The constants: the 20-letter alphabet, the alphabet with the gap character, the built-in conversion tables, and the pre-built `str.translate` / `bytes.translate` tables derived from them at import time. |
| `protfasta/protfasta_exceptions.py` | `ProtfastaException`. |
| `protfasta/scripts/pfasta.py` | The `pfasta` command-line tool, a thin client of `read_fasta` and `write_fasta`. |
| `protfasta/_version.py` | Generated by versioningit at build time from the git tag; not checked in. |
| `protfasta/data/test_data/` | The FASTA files the test suite reads, shipped with the package so the suite can run against an installed copy. |
| `protfasta/tests/` | The pytest suite: `test_protfasta.py` for the API and `test_pfasta_cli.py` for the command-line tool. |
| `benchmark/` | A synthetic FASTA generator and a driver that measures parse time and peak memory from 10k to 10M records; see its README. |

The import graph is a strict tree: `__init__` imports `io`, `protfasta` and `utilities`; `io` and `protfasta` import `utilities`; `utilities` imports `_configs`; everything imports `protfasta_exceptions`. Nothing imports upwards.

## The record model

Inside the package a parsed file is a `list[list[str]]`: one two-element list `[header, sequence]` per record, in file order. Headers have had the leading `>` removed (and the caller's `header_parser` applied, if any); sequences have been joined across line breaks and upper-cased. That is the only representation the sanitization steps ever see, and it is exactly what `read_fasta(..., return_list=True)` hands back.

The pairs are lists rather than tuples for one reason: residue conversion rewrites `entry[1]` in place, so a converted dataset reuses the same pair objects and the unconverted majority of sequences are never copied. Everything else treats the pairs as read-only and builds new lists of existing entries when it needs to drop some.

Duplicate detection never stores a sequence. Each sequence is reduced to a 16-byte blake2b digest (`_seq_hash`), and each record to a single digest of header, a NUL separator and sequence (`_record_hash`), so the bookkeeping for a file with ten million records is a few hundred megabytes of small `bytes` objects rather than a second copy of the file. Collisions at that digest length are not a practical concern.

## Anatomy of a `read_fasta` call

Take the default call, `sequences = protfasta.read_fasta('proteins.fasta')`. Information flows like this:

```
read_fasta(filename, ...)                                    [__init__.py]
  |
  |-- check_filename(filename)                               [io.py]
  |-- check_inputs(<every keyword>)                          [io.py]
  |
  |-- internal_parse_fasta_file(filename, ...)               [io.py]
  |     |-- _open_fasta(filename)          utf-8-sig, surrogateescape
  |     '-- _parse_fasta_all(fh, ...)      GC paused, header uniqueness
  |           '-- _iter_fasta_lines(fh)    the parser: lines -> (header, seq)
  |     => raw: list of [header, seq]
  |
  |-- _deal_with_duplicate_records(raw, action)             [protfasta.py]
  |     '-- fail_on_duplicates / remove_duplicates           [utilities.py]
  |         (skipped entirely when expect_unique_header=True)
  |-- _deal_with_duplicate_sequences(updated, action)       [protfasta.py]
  |     '-- fail_on_duplicate_sequences / remove_duplicate_sequences
  |-- _deal_with_invalid_sequences(updated, action, ...)    [protfasta.py]
  |     '-- fail_on_invalid_sequences / remove_invalid_sequences /
  |         convert_invalid_sequences                        [utilities.py]
  |
  |-- write_fasta(updated, output_filename)   only if output_filename given
  |
  '-- return updated                          if return_list=True
      return convert_list_to_dictionary(updated)   otherwise
```

### 1. Argument validation

`check_filename` insists that `filename` is a string or `os.PathLike`. This exists because `open()` accepts an integer and treats it as a file descriptor, so `read_fasta(0)` would otherwise silently read standard input.

`check_inputs` then checks every keyword before anything is opened: the boolean flags really are booleans, each action string is one of its allowed values, `output_filename` is a path, `correction_dictionary` (if given) is a dictionary whose keys are non-empty strings and whose values are strings, and the one incompatible combination, `expect_unique_header=True` with `duplicate_record_action='ignore'`, is rejected. If a `header_parser` was supplied it must be callable, and unless `check_header_parser=False` it is smoke-tested on the string `'this test string should work'` and must return a string. The point of doing all this first is that a typo in a keyword fails in a millisecond rather than after parsing a five-gigabyte file.

### 2. Parsing

`internal_parse_fasta_file` opens the file through `_open_fasta`, which turns every `OSError` (missing file, a directory, permissions) into a `ProtfastaException`. The file is opened in text mode as `utf-8-sig` with the `surrogateescape` error handler. The `-sig` strips a leading byte-order mark, which Windows editors add routinely and which would otherwise hide the first `>` and drop the first record. `surrogateescape` means bytes that are not valid UTF-8 (a Latin-1 accent in a header, say) become lone surrogate code points instead of raising, and are written back out as the original bytes by `write_fasta`, so a read/write round trip is lossless; a stray byte inside a sequence simply shows up later as an invalid residue.

The open handle goes to `_parse_fasta_all`, which drives the actual parser, `_iter_fasta_lines`. That generator consumes any iterable of lines (a file handle in production, a plain list in tests) and applies a handful of rules: trailing whitespace is stripped from every line, blank lines are skipped, a line starting with `>` begins a new record, anything else is sequence data appended to the current record, and text before the first header is ignored. When a new header arrives (or the input ends) the accumulated lines of the previous record are joined once and upper-cased, and the `(header, sequence)` pair is yielded. A header with no sequence lines after it is skipped. If a `header_parser` was supplied it is applied to each raw header here; if it raises, or returns anything other than a string, that is reported as a `ProtfastaException` naming the header, because a `None` header would otherwise make the record look like headerless sequence data and vanish.

`_parse_fasta_all` appends each pair to the result as a `[header, sequence]` list and, when `expect_unique_header=True` (the default), keeps a set of headers seen so far and raises on the first repeat. It also pauses Python's cyclic garbage collector for the duration of the loop and restores it afterwards, exceptions included: every pair is a GC-tracked container, and on large files the collector was spending about a fifth of the parse time scanning objects that cannot form cycles. The streaming engine does not do this, because user code runs between its yields.

Peak memory at the end of this stage is the parsed result itself, roughly 800 bytes per record, plus one record in flight. The raw file is never held in memory as a whole.

### 3. Duplicate records

A duplicate record is a repeat of the same header **and** the same sequence. `_deal_with_duplicate_records` dispatches to `fail_on_duplicates` or `remove_duplicates`, both of which walk the list computing `_record_hash` for each entry against a running set of digests. `read_fasta` skips this stage entirely when `expect_unique_header=True`, because unique headers already make a duplicate record impossible and the pass would only hash every sequence to find nothing. With the default arguments, then, this stage costs nothing.

### 4. Duplicate sequences

`_deal_with_duplicate_sequences` is the same shape one level down: `fail_on_duplicate_sequences` keeps a dictionary from `_seq_hash` digest to the first header seen (so its error can name both records), and `remove_duplicate_sequences` keeps just a set of digests and builds a new list of the first occurrence of each sequence. The default action is `'ignore'`, so by default nothing happens here either.

### 5. Invalid residues

This is the stage that does real work on a default call, since the default action is `'fail'`. `_deal_with_invalid_sequences` dispatches on the action:

* `'fail'` runs `fail_on_invalid_sequences`, which raises on the first sequence containing a character outside the 20-letter alphabet (or the 21-character alphabet with `-` when `alignment=True`).
* `'remove'` runs `remove_invalid_sequences`, which drops such sequences.
* `'convert'` and `'convert-ignore'` run `convert_invalid_sequences` and then, for `'convert'` only, re-run `fail_on_invalid_sequences` to catch anything the table could not fix; that error is re-raised with a banner saying the sequence was still invalid after conversion.
* `'convert-remove'` is not a case of its own: `read_fasta` implements it as two passes, `'convert-ignore'` followed by `'remove'`.
* `'ignore'` does nothing.

The validity test is `check_sequence_is_valid`, and its trick is to delete rather than to search. A pure-ASCII sequence (the overwhelmingly common case, established in O(1) by `str.isascii`) is encoded to bytes and passed through `bytes.translate` with a deletion table containing every valid residue; whatever is left over is, by construction, the invalid characters in order of appearance, so an empty result means the sequence is clean and the first byte of a non-empty result is the offending character. Non-ASCII sequences go through the equivalent `str.translate` table. Both tables are built once in `_configs.py`.

The three dataset-level functions do not call that test once per record. They work in batches of 512 records (`_BATCH`): the sequences of a batch are concatenated and the deletion test is applied to the concatenation in one pass (`_batch_is_valid`), which needs no separator because deleting every valid residue from the concatenation leaves exactly the invalid characters of every member. A clean batch, which is nearly all of them on real data, is accepted without ever looking at an individual sequence; only a batch that fails is examined record by record, so the reported offender is still the first invalid sequence in file order.

Conversion is built the same way. `_make_converter` turns a correction dictionary (the built-in table from `_configs.py` unless the caller supplied one) into a function of one sequence. Where every key is a single character the function is a `str.translate` call with a pre-built table; a dictionary with any multi-character key falls back to sequential `str.replace` calls in dictionary order. Either way the function first checks whether any of the table's keys is present at all, with a few C-level `in` scans, and returns the very same string object if not, which is how `convert_invalid_sequences` can tell a converted sequence from an untouched one by identity. It, too, works a batch at a time: the joined batch is scanned once for each key, and a batch containing none of them is skipped outright.

### 6. Writing the result out

If `output_filename` was given, the sanitized list is handed to `write_fasta` exactly as a caller would hand it, so the file that lands on disk is byte-for-byte what a separate `write_fasta` call would produce. This happens before the dictionary is built, which means the written file always contains every surviving record even when duplicate headers would collapse in the dictionary.

### 7. Shaping the return value

With `return_list=True` the list of pairs is returned as is. Otherwise `convert_list_to_dictionary` builds the dictionary, which in the non-verbose case is a single `dict(list_of_pairs)` call. If two surviving records share a header the later one wins; that can only happen with `expect_unique_header=False`, and it is the reason the documentation steers such callers towards `return_list=True`.

With `verbose=True` each stage prints one `[INFO]` line summarising what it did; the messages are produced by the workflow functions in `protfasta.py`, not by the utilities, so the utilities stay silent and reusable.

## Anatomy of a `write_fasta` call

`write_fasta` is deliberately dumb: it does not sanitize, convert or de-duplicate anything. It takes what it is given, checks that it is writable as FASTA, and writes it.

```
write_fasta(fasta_data, filename, linelength=60, append_to_fasta=False)   [__init__.py]
  |
  |-- normalise the container:  dict -> .items(),  list -> check each element is a pair
  |-- normalise linelength:     None/False/<1 -> single line,  1..4 -> 5,  else int()
  |-- validate every record:    header is a str with no line break,
  |                             sequence is a non-empty str with no line break
  |
  |-- _open_output(filename, append)      utf-8, surrogateescape, 1 MiB buffer   [io.py]
  '-- for each record:  fh.write(_format_record(header, seq, linelength))       [io.py]
```

### 1. Normalising the input

A dictionary is treated as `header -> sequence` and iterated through `.items()`. A list must consist of two-element lists (or tuples) of `[header, sequence]`; the element type is checked as well as its length, because a bare two-character string would otherwise unpack into a one-character header and a one-character sequence. Anything else raises. `append_to_fasta` must be a boolean.

`linelength` is coerced with `int()`, so a numeric string is accepted and a non-numeric one raises a `ProtfastaException` rather than a `TypeError`. `None`, `False`, `0` and negative values all mean "one line per sequence"; `1` to `4` are clamped to `5`.

### 2. Validating before touching the filesystem

Every record is checked before the output file is opened: the header must be a string without a line break, the sequence must be a non-empty string without a line break. A line break inside either would be read back as a record boundary, silently corrupting the file, and a non-string sequence would either crash inside the formatter or be `str()`-ed into the file. Doing this pass first is what makes the function atomic in practice: a bad entry three million records in raises without creating, truncating or partially appending to `filename`.

### 3. Writing

`_open_output` opens the file for writing (or appending) as UTF-8 with `surrogateescape`, so headers that arrived from a non-UTF-8 file via `read_fasta` go back out with their original bytes, and with a 1 MiB buffer so that very large outputs do not pay a system call per record. Every `OSError` becomes a `ProtfastaException`.

Each record is then rendered by `_format_record`: the header line, the sequence sliced into `linelength` chunks joined by newlines, and a blank separator line, assembled into one string and emitted with a single `write` call. The output for a record is therefore `>header\n` followed by the wrapped sequence and an empty line. The streaming reader's `output_filename` tee calls the same function, so a file written while streaming is identical to one written by `write_fasta` afterwards.

## Where the streaming reader differs

`read_fasta_stream` exists for files that do not fit in memory, and it is built from the same parts. It runs the same `check_filename` and `check_inputs` up front (plus an eager existence check on the input, and a check that `output_filename` is not the same file as the input, resolving symlinks), then returns the generator `_stream_fasta`. That generator opens the input through `_open_fasta`, opens the output through `_open_output` only afterwards (so a missing input never leaves an empty output file behind), and pulls records from `_iter_fasta_lines` one at a time, applying the same steps in the same order per record: header uniqueness against a running set, duplicate records against a set of `_record_hash` digests, duplicate sequences against `_seq_hash` digests, then the invalid-residue action using `check_sequence_is_valid` and a converter built once by `_make_converter`. Surviving records are tee'd to the output file with `_format_record` and yielded as `(header, sequence)` tuples, or `[header, sequence]` lists with `return_list=True`.

Two consequences follow from streaming. Data-dependent errors are raised mid-iteration, at the offending record, because there is no earlier moment at which they could be known. And the per-record bookkeeping is the only thing that grows with the file, which is why the streaming defaults turn the header-uniqueness and duplicate-record checks off and why a one-time warning is emitted when a caller turns any of them back on. The batch tricks of the load-everything path are not used here; a batch would have to be buffered before any of its records could be yielded, which would move the point at which an error surfaces.

## The command-line tool

`pfasta` is a client of the API, not a second implementation. It maps its flags onto `read_fasta` keywords (the `convert-all` / `convert-res` families become `invalid_sequence_action` plus `alignment`; `--remove-comma-from-header` becomes a `header_parser`), always asks for `return_list=True`, applies its own length filters and random sub-sampling to the resulting list of pairs, optionally prints length statistics, and hands the list to `write_fasta`. A `ProtfastaException` from either call is printed as a single `[FATAL ERROR]` line and the process exits with status 1; if the filters leave nothing, it says so and exits with status 0 without writing a file.

## Tests and benchmarks

The suite lives in `protfasta/tests/` and is shipped with the package, so it can be run against an installed copy with `pytest --pyargs protfasta.tests`; that is what `tox` and the CI matrix do across every supported Python version. The FASTA fixtures in `protfasta/data/test_data/` are located through `protfasta._get_data('test_data')`, and anything a test writes goes to a pytest temporary directory. Beyond the per-function tests, two classes are worth knowing about when changing the pipeline: `TestReadFastaStreamParity` runs every test file through every invalid-residue action under both `read_fasta` and `read_fasta_stream` and asserts they agree, and `TestBatchedValidation` plants an offender at each batch boundary to make sure the batched validation and conversion never miss one.

The `benchmark/` directory measures where the time and memory go at scale; its README carries reference numbers for 10k to 10M records and is the place to look before and after touching anything on the hot path.
