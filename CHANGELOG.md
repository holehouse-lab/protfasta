# Changelog

All notable changes to **protfasta** are recorded here, newest first. Version numbers come from git tags via versioningit, so a `pip install protfasta` gets whichever tagged release is current.

* **0.1.28** (November 2026) - Dropped Python 3.9; Python 3.15 is now fully supported.
	* **protfasta** now requires Python 3.10 or higher. Python 3.9 reached end-of-life in October 2025 and GitHub's current runner image (Ubuntu 26.04) no longer provides it, so we can't test against it any more. No code changed in this release, so `pip` on Python 3.9 will keep installing 0.1.27, which behaves identically.
	* Python 3.15 is out of pre-release, so its test job now has to pass like every other one (it used to be allowed to fail), and it's listed in the package classifiers.
	* The package moved to a `src` layout (`protfasta/` is now `src/protfasta/`). Nothing changes for anyone installing from PyPI, and import names are the same. An editable install is now a plain `.pth` file pointing at `src/` rather than an import hook, so static tools (Pylance/pyright, mypy) in other projects can resolve it. If you have an existing editable install, re-run `pip install -e .` from the repository root after pulling; the old one points at a directory that no longer exists.

* **0.1.27** (November 2026) - Content before the first header is no longer dropped silently, plus the fixes from a full code review.
	* **Behavior change:** anything before the first `>` header used to be thrown away without any message by both `read_fasta(...)` and `read_fasta_stream(...)`. That meant a file with no recognisable header at all - a gzipped FASTA file, a UTF-16 one, a file that simply isn't FASTA - read "successfully" as zero records, and a first header that had picked up a leading space (` >a`) took its whole record with it. Any non-blank line before the first header now raises a `ProtfastaException` quoting the line number and the (truncated) line by default. The new `leading_content_action` keyword controls this: `'fail'` (default) or `'remove'` (discard it - the old behaviour, now reported when `verbose=True`). Blank lines before the first header are still fine, and an empty file still gives no records. Pass `leading_content_action='remove'` to restore the old behavior.
	* When streaming, the check runs at the first `next()`, before `output_filename` is opened, so an input that turns out not to be FASTA never creates or truncates the output file.
	* `pfasta` has a matching `--leading-content {fail,remove}` option (default `fail`). A compressed or non-FASTA input now gives a `[FATAL ERROR]` and exit status 1, rather than `0 sequences remain after filtering` and exit status 0.
	* Fixed non-ASCII characters being silently turned into valid residues on read. Sequences were upper-cased with `str.upper()`, which applies the full Unicode case mapping: `ß` became `SS`, `ſ` became `S`, `ı` became `I` and `ﬁ` became `FI`, all of which then passed default validation (and two of which changed the length of the sequence). Only the letters `a`-`z` are upper-cased now, so anything else reaches `invalid_sequence_action` exactly as it is in the file.
	* **Behavior change:** a sequence that conversion leaves with nothing in it (`***` under the built-in table, say) used to come back from `read_fasta(...)` and `read_fasta_stream(...)` as a record with an empty sequence, whatever `empty_sequence_action` said. It is now handled by `empty_sequence_action` like any other empty record: an error by default, dropped under `'remove'` (and counted when `verbose=True`), kept under `'ignore'`.
	* `read_fasta_stream(..., output_filename=...)` now runs every record through the same checks as `write_fasta(...)` before writing it. Previously the stream formatted records straight to disk, so it could write a file that `write_fasta` would have refused and that did not read back as the records it had yielded - a `header_parser` that put a line break into a header was enough.
	* `write_fasta(...)` (and so `output_filename` in both readers) now refuses a sequence that would not read back unchanged once wrapped: one where a line would start with `>` (read back as a header, splitting the record in two) or end in whitespace (stripped on the way back in). Only a sequence that was never validated can contain either. A sequence with a `>` or a space that does *not* land on a line boundary still round-trips and is still written.
	* `write_fasta(...)` no longer lets anything but a `ProtfastaException` escape, and no longer truncates the output on bad data: a `filename` that is not a path (`None`, or an integer, which was taken for a file descriptor - `write_fasta(data, 1)` wrote to stdout and closed it), a path containing a NUL byte (also in `read_fasta(...)` and `output_filename`), `linelength=float('inf')`, and a header or sequence holding a lone surrogate that did not come from a file. The last of these used to raise `UnicodeEncodeError` part-way through the write, after the existing file had already been truncated; it is now caught in the validation pass, before the file is opened. `linelength=True` (which wrote 5 residues per line) and a float with a fractional part (which was rounded down) are now refused as well.
	* `read_fasta(...)` now emits a warning when a dictionary return loses records. With `expect_unique_header=False` records that share a header overwrite one another in the returned dictionary (the last wins); that is documented and unchanged, but it used to happen without a word unless `verbose=True`. The warning gives the number lost and points at `return_list=True`.
	* A `correction_dictionary` with `-` in one of its keys is now refused when `alignment=True`. The two contradict each other (preserve gaps / convert gaps), and the dictionary used to win silently, despite the documentation saying gaps are never converted in alignment mode.
	* **Behavior change:** a `correction_dictionary` with a multi-character key is now applied in a single pass, like one with only single-character keys always has been. It used to be a chain of `str.replace` calls in dictionary order, so the output of one key could be converted again by the next, and the same single-character keys gave different results depending on whether a multi-character key happened to be present (`{'B': 'X', 'X': 'G'}` turned `ACBXD` into `ACXGD`, but adding `'QQ': 'Q'` made it `ACGGD`). Now a replacement is never converted a second time, dictionary order no longer matters, and where two keys match at the same position the longer one wins. If you relied on chaining, write the final value into the dictionary directly.
	* An invalid residue that cannot be seen (a tab, a space, a NUL, a stray non-UTF-8 byte) is now shown as its quoted escape in the error message (`Failed on invalid amino acid: '\t'`) rather than printed raw. Visible characters are reported as before.
	* `read_fasta_stream(...)` now checks that `silence_warnings` is a boolean (`silence_warnings='no'` used to silence the warning).
	* The duplicate-record error message had its colon on the wrong line (`...the following record\n:>header`); it now reads `...the following record:\n>header`.
	* The verbose conversion summary now reads `Converted invalid residues in N sequences`; it used to claim the sequences had been converted "to valid sequences", which is not true under `convert-ignore`.
	* `pfasta` fixes:
		* It now refuses to write its output over its own input (`pfasta in.fasta -o in.fasta`, or any run on a file called `output.fasta` with no `-o`), which used to replace the input with the filtered result and exit 0. The files themselves are compared, so a symlink or a differently-capitalised name counts.
		* `--print-statistics` quantiles were biased upwards (the median of 10 and 20 was reported as 20, and the 75th percentile of four lengths as the longest). They are now interpolated, and printed to one decimal place.
		* New `--random-seed <int>` option, so a `--random-subsample` can be reproduced.
		* Adjacent length bounds (`--shortest-seq 3 --longest-seq 4`) are now rejected like equal ones, since both bounds are exclusive and nothing can pass.
		* An option given an empty value (`-o ''`, `--duplicate-record ''`, ...) is now an error rather than quietly meaning "use the default".
		* The `--help` text for `--silent` no longer says it prints nothing at all; a `[FATAL ERROR]` is still printed.
	* Packaging and CI: a checkout with no tags built as version `1.0.0` (and one with no git information as `1+unknown`), above every real release; the fallbacks are now `0.0.0` and `0+unknown`. The GitHub Actions workflow now fetches the full history, since the default shallow checkout has no tags to take the version from.
	* Benchmark driver: the cached input file's name now includes the seed (a different `--seed` used to get the old file back), inputs are generated under a temporary name and renamed when complete (an interrupted run used to leave a truncated file that was then reused), an existing `PYTHONPATH` is extended rather than replaced, and `--repeats 0` is rejected up front.
	* Test suite: every test that only checked that *some* exception was raised now checks which one (a message fragment, or the exit code for `pfasta`); the tests that only checked an output file existed now read it back and check its contents; the two verbose tests whose assertions could not fail now assert the exact counts; and new tests cover behaviour that nothing pinned down before, found by breaking the code on purpose and seeing what the suite let through (the stream keeping duplicate records by default, the stream replacing rather than appending to an existing output file, the per-step verbose counts, silence when `verbose=False`, the `linelength` clamping boundaries, and the `pfasta` defaults for unique headers, alignments, line length and statistics among them).
	* Documentation: `mypy .` is clean again (`docs/conf.py`), the README's test instructions now include the install step a fresh clone needs, Example 9 no longer recommends a call that loses records, and the pages now spell out a consequence of the processing order: the duplicate checks run before conversion, so sequences that only become identical once converted are both kept.

* **0.1.26** (October 2026) - Headers with no sequence are no longer dropped silently.
	* **Behavior change:** a header with no sequence after it (for example `>a` immediately followed by `>b`, or a header on the last line of the file) used to be skipped without any message by both `read_fasta(...)` and `read_fasta_stream(...)`, so records could go missing unnoticed. Such records now raise a `ProtfastaException` naming the header by default. The new `empty_sequence_action` keyword controls this: `'fail'` (default), `'remove'` (drop the record - the old behaviour, now reported when `verbose=True`) or `'ignore'` (keep the record with an empty sequence; not allowed together with `output_filename`, since an empty sequence cannot be written). Empty records are handled before the header-uniqueness check, so `'remove'` gives exactly the results of earlier versions. Pass `empty_sequence_action='remove'` to restore the old behavior.
	* `pfasta` has a matching `--empty-sequence {fail,remove}` option (default `fail`).

* **0.1.24** (September 2026) - Bug fixes, and a performance and memory pass over the whole pipeline.
	* Fixed silent data loss when a FASTA file starts with a UTF-8 byte-order mark (which Windows editors add routinely). The BOM hid the first `>` so the first record was dropped without any error. Files are now always decoded as UTF-8 (rather than whatever the platform locale happens to be) with the BOM stripped.
	* Fixed a crash on files containing bytes that are not valid UTF-8 (e.g., a Latin-1 accent in a header), which raised an unhandled `UnicodeDecodeError`. Such bytes are now carried through and written back out unchanged, so a read/write round trip is lossless; a stray byte inside a sequence is reported as an invalid residue like any other. Error messages that quote such data are guaranteed to be printable.
	* Fixed duplicate *record* detection in `read_fasta(...)` missing a duplicate when the same header had already appeared with a different sequence - the lookup only remembered the first sequence seen per header. `read_fasta_stream(...)` already handled this correctly, so the two disagreed on the same file. Both now key each record on a single 16-byte digest of header plus sequence, which also uses roughly a quarter of the memory of the old per-header structures under `duplicate_record_action='remove'`.
	* `read_fasta(...)` and `read_fasta_stream(...)` no longer hash every sequence to look for duplicate records when `expect_unique_header=True` (the `read_fasta` default): unique headers already rule out duplicate records, so that pass could never find anything. `read_fasta_stream`'s memory warning no longer blames `duplicate_record_action` in that case either.
	* Fixed the `-res` variants of `pfasta --invalid-sequence` on actual alignments. `convert-res` raised on every gapped sequence and `convert-res-remove` discarded all of them, because the CLI stripped `-` from its conversion table but still read the file as a plain (non-alignment) FASTA. They now read the file as an alignment, as documented. All the `convert-*` modes also now use protfasta's built-in conversion table, so whitespace inside a sequence is converted rather than failing.
	* `pfasta` now reports data problems (a duplicate record, an invalid residue, an unwritable output path, ...) with a single `[FATAL ERROR]` line and exit status 1 instead of a Python traceback.
	* `pfasta` can now also be run as `python -m protfasta.scripts.pfasta`; previously the module had no `__main__` guard, so that invocation silently did nothing.
	* `write_fasta(...)` now validates every entry *before* opening the output file. Previously an empty sequence part-way through the data raised after the earlier records had already been written, leaving a truncated file (or a half-appended one with `append_to_fasta=True`). An output path that cannot be opened now raises a `ProtfastaException` rather than an `OSError`, from `write_fasta(...)`, `read_fasta(..., output_filename=...)` and `read_fasta_stream(..., output_filename=...)` alike.
	* `read_fasta_stream(...)` now raises immediately, at call time, when `filename` does not exist (rather than at the first `next()`), opens the input before creating `output_filename` (so a missing input no longer leaves an empty output file behind), and checks that `output_filename` is a different file from `filename` by comparing the files themselves rather than their paths. Previously a symlink, a hard link or, on a case-insensitive filesystem such as the macOS default, a differently-capitalised name for the input (`Data.fasta` versus `data.fasta`) passed the check, and opening the output truncated the input to zero bytes before a single record had been read.
	* `write_fasta(..., append_to_fasta=True)` on a file whose last line had no line break glued the first new header onto the end of that line, so it was read back as sequence data and the appended record silently merged into the previous one. A line break is now written first when one is needed.
	* `write_fasta(...)` accepted a sequence consisting only of whitespace, which vanished when the file was read back (the reader skips blank lines, leaving a header with no sequence). Such sequences are now rejected along with empty ones.
	* Duplicate-record detection could treat two different records as the same one when a header contained a NUL byte: the header and sequence were hashed with a NUL separator, so `('A\0', 'B')` and `('A', '\0B')` produced the same digest and one of them was removed (or reported) as a duplicate of the other. `read_fasta(...)` now compares records exactly (see below), and the digest used by `read_fasta_stream(...)` includes the header's length so the split can no longer be ambiguous.
	* A `correction_dictionary` with an empty-string key silently corrupted every sequence (the replacement was inserted between every pair of residues), and a non-string value produced garbage. Keys must now be non-empty strings and values strings; anything else raises a `ProtfastaException` up front.
	* A non-callable `header_parser` with `check_header_parser=False` raised a `TypeError` mid-parse; it is now rejected as a `ProtfastaException` before the file is read. A `header_parser` that raises on a real header also now surfaces as a `ProtfastaException` naming the offending header.
	* A `header_parser` that returned something other than a string for a header - `None` from a regular expression that did not match being the classic case - made `read_fasta(...)` and `read_fasta_stream(...)` silently drop that record, because a `None` header looked like sequence data with no header. Both now raise a `ProtfastaException` naming the offending header. The header-parser examples in the documentation also assumed every header contained a `|`, which made them fail the default smoke test; they have been fixed.
	* `write_fasta(...)` could write a corrupt file without complaint: a line break inside a header or sequence was written verbatim and read back as a record boundary, a non-string sequence was either crashed on with a raw `TypeError` (when line-wrapped) or `str()`-ed straight into the file (when not), and a flat list of two-character strings passed the list check and was written out as garbage records. Headers and sequences must now be strings without line breaks, list elements must be two-item lists or tuples, and `append_to_fasta` must be a boolean; anything else raises a `ProtfastaException` before the file is touched.
	* `read_fasta(..., output_filename='')` silently wrote nothing; an empty path is now reported as unwritable like any other bad path.
	* `pfasta` fixes: the error for a missing filename carried a doubled `pfasta: error:` prefix; `--number-lines 0` was silently replaced by the default of 60 rather than rejected (the minimum is 5); equal `--shortest-seq` and `--longest-seq` values were accepted even though both bounds are exclusive, so nothing could ever pass; `--random-subsample 0` wrote an empty output file instead of reporting that no sequences remain; and `--non-unique-header` had no `--help` text.
	* Performance. On a 145 MB, 200,000-record file the default `read_fasta(...)` call is ~2.7x faster and the default `read_fasta_stream(...)` call is ~2.6x faster, with no change to the parser itself (which was already close to the limit for pure Python):
		* Invalid-residue checking is ~8x faster. Every valid residue is deleted from the sequence in one C-level pass (`bytes.translate` for ASCII data), so an empty result means the sequence is clean and anything left over is the first invalid character.
		* Residue conversion is ~2-5x faster. The converter now checks whether any convertible character is actually present before touching the sequence, and returns the input untouched when there is nothing to do; with a custom `correction_dictionary` the translation table is built once per call to `read_fasta`/`read_fasta_stream` rather than once per sequence.
		* On top of that, `read_fasta(...)` now validates and converts in batches of 512 records: each batch is joined and examined with a few C-level passes, and only a batch that actually contains an invalid (or convertible) character is examined record by record. On clean data this makes `invalid_sequence_action='fail'` / `'remove'` a further ~1.5x faster and the `convert` actions ~2x faster than the per-record versions.
		* `write_fasta(...)` is ~1.5x faster: each record is assembled into a single string and written with one call instead of one call per line.
		* `read_fasta(...)` pauses Python's cyclic garbage collector for the duration of the parse (restoring it afterwards, exceptions included). Every `[header, sequence]` pair is a GC-tracked object, so on large files the collector was running thousands of times to scan objects that cannot form cycles - about 20% of the parse time at ten million records. The streaming parser is unaffected, since user code runs between its yields.
	* `read_fasta(...)` now detects duplicate records and duplicate sequences by comparing the strings it already holds, rather than by computing a 16-byte blake2b digest of every sequence. The comparison is exact, the bookkeeping is references to existing strings rather than millions of digest objects, and the duplicate stage itself is 3.6-5x faster; at a million records `duplicate_sequence_action='remove'` goes from 2.93 s to 2.29 s end to end and uses ~45 MB less memory, `'fail'` ~90 MB less. Duplicate records are keyed on the header, with a sequence comparison only when a header recurs, so a file whose headers are mostly unique never hashes a sequence at all. `read_fasta_stream(...)` still uses digests, since it does not keep the records it has already yielded.
	* `read_fasta_stream(..., duplicate_sequence_action='remove')` no longer holds on to every header it has seen (only `'fail'` needs them, to name both records in its error message), which cuts its memory growth from ~280 to ~120 bytes per record (1.2 GB rather than 2.8 GB at ten million records).
	* Added a `benchmark/` directory with a synthetic FASTA generator and a driver that measures parse time and peak memory for `read_fasta` and `read_fasta_stream` at 10k, 100k, 1M and 10M records; see `benchmark/README.md` for reference numbers.
	* Added `ARCHITECTURE.md`, a walkthrough of how a `read_fasta` and a `write_fasta` call move through the modules, for anyone changing the package rather than using it.
	* Packaging: the license is now declared in the SPDX form that current setuptools expects (the old table form is deprecated and due to become a build error), and the project metadata gained classifiers and documentation/source/issue URLs. The Read the Docs version shim in `protfasta/__init__.py` is anchored on the package location rather than the working directory.
	* Cleaned up the type annotations (`filename`/`output_filename` are declared as accepting path-like objects) and the code now passes `mypy` and `ruff` cleanly.
	* Removed leftover scaffolding: the Travis CI, LGTM and codecov configurations (none of which have been used since the move to GitHub Actions and tox), the `devtools/` conda helpers, the cookiecutter sample data that was being shipped inside the package, the 2020 shell-script test for `pfasta` (superseded by the pytest CLI suite), the `tests/outdata/` scratch directory (the tests write to temporary directories) and the yapf, flake8 and `setup.py` alias sections of `setup.cfg`, which now holds only the coverage.py configuration.

* **0.1.23** (July 2026) - Bug fixes and more robust error handling.
	* Fixed a crash when a FASTA file contained non-ASCII characters in a sequence. Duplicate detection hashes every sequence before invalid-residue handling runs, and the hashing step used an ASCII encoder, so any non-ASCII byte raised an unhandled `UnicodeEncodeError` instead of being reported (or removed/converted) as an invalid residue. This affected `read_fasta(...)` with its default options.
	* All file-open failures now raise a `ProtfastaException`. Previously only a missing file was handled, so passing a directory or an unreadable file raised a raw `OSError`.
	* `write_fasta(...)` now raises a `ProtfastaException` when handed something that is neither a dictionary nor a list (it previously raised an `UnboundLocalError`) and when `linelength` cannot be interpreted as an integer (it previously raised a `TypeError`). A numerical string such as `linelength='60'` is now accepted.
	* `pathlib.Path` objects are now accepted anywhere a filename is expected, including the `output_filename` keyword, which previously required a string. Passing a non-path (such as an integer, which `open()` would have silently treated as a file descriptor) now raises a `ProtfastaException`.
	* Three input-validation error messages named the wrong keyword (`invalid_sequence`) when reporting a bad `duplicate_record_action`, `duplicate_sequence_action`, or `invalid_sequence_action`.
	* `pfasta` no longer ignores `--shortest-seq 0`, `--longest-seq 0`, and `--random-subsample 0`, which were silently dropped because zero is falsy. Also tidied up the `--help` text for the length filters and fixed some typos in the `--print-statistics` output.
	* Added the `py.typed` marker file, which was declared in `pyproject.toml` but missing from the package, so the type annotations are now visible to type checkers.
	* Raised the minimum supported Python version to 3.9. The previous floor of 3.7 had not been tested for some time - both are long past end-of-life.
	* Extended the test matrix to cover Python 3.9 through 3.14, plus the Python 3.15 pre-release (which is allowed to fail without blocking the build). The full test suite passes on all of them.

* **0.1.22** (July 2026) - Updated the Read the Docs build configuration.

* **0.1.20 and 0.1.21** (July 2026) - Change defaults for `protfasta.read_fasta_stream(...)` 
	* Previously the default options for `protfasta.read_fasta_stream(...)` led to a small O(N) memory growth due to duplicate record sanity checking. We have now changed the default behavior to not check for duplicates, ensuring `protfasta.read_fasta_stream(...)` is truly memory flat. We also include a warning if options are passed to `protfasta.read_fasta_stream(...)` that will not yeild a flat memory implementation. Note that even if this is the case, the memory footprint here remains much smaller than for the `read_fasta(...)` implementation.
	* Update to readme (for 0.1.21)
	
* **0.1.19** (July 2026) - Streaming reads with full sanitization.
  * New `protfasta.read_fasta_stream(...)` - a streaming counterpart to `read_fasta` with an identical signature. It returns a generator that yields `(header, sequence)` tuples (or `[header, sequence]` lists with `return_list=True`) one record at a time, applying the same sanitization pipeline as `read_fasta` (duplicate handling, invalid-residue handling, alignment support, custom header parsing). Peak memory stays bounded to roughly one record, so files larger than RAM can be processed in a single pass. Sanitized output can be teed to disk as it streams via `output_filename`.
  * **Breaking change:** removed the public `protfasta.iter_fasta` generator that was introduced in 0.1.18. `read_fasta_stream` supersedes it - it provides the same streaming access plus the full sanitization pipeline. For the closest drop-in equivalent (streaming with no checks), use `read_fasta_stream(f, expect_unique_header=False, duplicate_record_action='ignore', invalid_sequence_action='ignore')`; or just `read_fasta_stream(f)` to additionally gain header-uniqueness, duplicate, and invalid-residue validation.
  * Added a dedicated `read_fasta_stream` documentation page and worked examples, including guidance on when to use `read_fasta_stream` vs `read_fasta`.
  * Test suite expanded with 21 new tests covering the streaming parser.

* **0.1.18** (April 2026) - Performance overhaul for large FASTA files (hundreds of millions of sequences).
  * `read_fasta` now streams the input file instead of reading it entirely into memory with `readlines()` — peak memory is now O(single record) rather than O(file size).
  * New `protfasta.iter_fasta(filename, header_parser=None)` generator for memory-bounded streaming access to `(header, sequence)` pairs from files that don't fit in RAM.
  * Core parser rewritten to use list-of-parts + `''.join()` instead of quadratic string concatenation, and to skip header-uniqueness tracking entirely when `expect_unique_header=False`.
  * `convert_to_valid` / invalid-residue handling now uses a pre-built `str.translate` table (single C-level pass) instead of a chained `str.replace` loop — typically 5–20× faster.
  * `check_sequence_is_valid` now uses frozenset membership instead of list-based `in` scans.
  * Duplicate-detection utilities (`fail_on_duplicates`, `remove_duplicates`, `fail_on_duplicate_sequences`, `remove_duplicate_sequences`) now store 16-byte blake2b digests instead of full sequences in their lookup structures, dramatically reducing peak memory for files with long sequences.
  * `write_fasta` replaced its per-residue `fh.write()` loop with chunked slice writes and opens the output with a 1 MiB buffer — roughly two orders of magnitude faster on large files.
  * All existing behavior and the full test suite (239 tests) are preserved.
